# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Painless is a lightweight React SPA template/demo (RealWorld conduit app) that emphasizes zero SSR, zero-runtime CSS (Linaria), and type-safe TypeScript. It fetches data from `https://api.realworld.io/api/`. Private package, not published to npm.

## Design Principles

These are intentional design decisions, not missing features. Do not suggest adding SSR, server actions, nested routes, state management libraries, structural sharing in the query layer, or platform-specific optimizations.

- **Pure client-side SPA** — No SSR/SSG. SEO can be handled by serving pre-rendered HTML to bot traffic via headless browser, not by contaminating the app architecture.
- **Frontend is not the backend** — API Routes/Server Actions belong in dedicated backend frameworks. The web frontend is one of many clients; coupling it with the backend serves only one client.
- **Flat routing** — The route is the page. Nested/parallel routes decompose page state into URL fragments, adding unnecessary complexity. Independent UI sections are components, not routes.
- **No state management libraries** — Proper page/component decomposition keeps state local. Use React primitives (`useState`, `useContext`, `useRef`) and `useControl` from `react-use-control` (direct dependency) for component state exposed to hosts via props.
- **No structural sharing in the query layer** — Refetches settle new references; content-identical background revalidations re-render subscribers. Deep equality is O(payload) on every fetch; a hot component takes scalar props behind `React.memo` instead (object props are always new references after settle, so memo boundaries must compare scalars).
- **No built-in image optimization** — Image optimization is a service concern, not a framework concern. A dedicated service serves all clients, not just the frontend.
- **Platform-agnostic deployment** — Produces standard static assets. No vendor lock-in to any deployment platform.
- **No framework-level loader→view typing** — the data↔view match is closed at the declaration site by the `createDataLoader` triplet (typed hook + DEV identity check), not by the router; the raw generic `useData<T>()` channel keeps manual annotations and accepts the drift risk. Views stay path-agnostic and deep components keep context reads (see the "Loader→view typing" note under Architecture).

## Architecture

**Routing:** `@native-router/react` 1.15.x with `HistoryRouter` defined in `src/views/index.tsx`. Routes are a module-level object declared via `createRoutes({...})` — satisfies semantics: checked against `Route` while every `path` keeps its string-literal type (`as Route` widens paths to `string`) — with lazy `import()` views, inline async `data` loaders, route guards (`beforeLoad`/`redirect`), route-level `params` schemas (core ≥1.9 `route.params`, same hand-written Standard Schema style — see `src/types/params.ts`; `/editor/:slug` trims/validates the slug after matching and before guards/loaders, and an invalid slug fails the resolve as a `ParamsError` through the global `errorHandler`, while data-phase failures go to the route `errorComponent`), and optional route-level `search` schemas (Standard Schema — see `src/types/search.ts`; the parsed/coerced search reaches the loader as `ctx.search` and components via `useSearch(schema)`; since react 1.6 / core 1.8, `createRoutes` **derives** the `ctx.search` type from the route's schema — the former `{search: HomeSearch}` callback annotations are gone, and a callback annotation contradicting the schema is a compile error at the route property; schema-less levels degrade to the raw `SearchInput`; an explicit `Route<P, S>` generic still wins over inference). `export type AppPaths = RoutePaths<typeof routes>` extracts the path-pattern union for `TypedLink<AppPaths>` (compile-time path checking; parameterized patterns additionally require `params` — used by RouterError, Article/NotFound, Login, Register; since react 1.15 `TypedLinkProps` passes `prefetch` through — declared, the link renders via `PrefetchLink` internally — so `PreviewLink` wraps `TypedLink<AppPaths>` with a literal `/article/:title` + `params={{title: slug}}` target and a built-in `prefetch='viewport'` default, overridable per call). Search *writes* go through `useSetSearch(homeSearchWriteSchema)` (Home pagination/tag, Tags): the input is given in the URL-side string form, coerced by the shared `parseHomeSearch` core, and default-equal fields (offset 0 / limit 10) are stripped so URLs stay clean — read and write share the one contract. Since 1.4 a route-level render error boundary catches component-subtree throws and renders the route's `errorComponent` with `ctx.phase === 'render'` (resolve-phase failures carry no `phase`); without a route `errorComponent` the error reaches the global `errorHandler`. The `errorHandler` prop renders `RouterError` for generic route failures (works from cold start since 1.2.1); `/article/:title` additionally declares a route-level `errorComponent` (`src/views/Article/NotFound.tsx`) that renders "Article not found" vs "Failed to load: message" (duck-typed `status === 404`) with a back-to-home link. Unmatched paths instead of the global error page render the Router-level `notFound` view (`src/views/NotFound.tsx`, native-router ≥1.14 prop — dedicated 404, back/forward onto the entry replays it); the global `errorHandler`'s `RouterError` renders the raw stack trace only in DEV builds (production shows message + Refresh + Home only). `StackWarmer`'s guard-skip check derives its guarded path prefixes from the routes table (children declaring `beforeLoad`) — no hand-maintained prefix constant. `ScrollRestoration` is mounted in `Layout` — back/forward restores scroll position. Home article cards use `PreviewLink` (a `TypedLink<AppPaths>` with a built-in `prefetch='viewport'`) — data + chunk prefetch when the card scrolls into view, hover preview stays intact.

**Loader→view typing: solved at the declaration site; the generic channel stays manual (do not "fix" it):** App-level views consume route data through the `createDataLoader` triplet's second element — a typed `useXxxData()` hook with a DEV `route.data === loader` identity check (`src/util/dataLoader.ts`) — which closes the data↔view match at the declaration site (`src/services/dataloaders.ts`); views write no `useData<T>()!` casts. The raw generic `useData<T>()` channel (kept for consumers that skip the factory) still has no compile-time link to the loader's return type; that drift risk is accepted. Evaluated and rejected in the 2026-08 review: (1) a from-argument (`useData('/articles/:slug')`, TanStack's `useLoaderData({from})` shape) makes every view aware of its own mount path — but data/view matching is the router config layer's job; a view should only know "what data I render", never "where I am mounted"; (2) a props protocol (`component: ComponentType<{data: D}>`, checked by `createRoutes` at the config site) puts the check at the correct layer, but deep child components would need prop drilling — a real daily cost paid for a one-time annotation debt. Decision: the factory triplet is the accepted resolution for app routes; the generic channel keeps the status quo. Revisit only when a channel appears that couples neither paths nor props (TypeScript language evolution or a library-side structural change).

**In-app navigation keeps the old view by design (do not "fix" this):** native-router maps the browser's native navigation semantics — while a navigation chain is in flight, the old view stays rendered (old document stays visible until the new one commits) with only the global `Loading` bar as the tab-spinner equivalent. The URL is pushed only *after* the chain settles (`history.push` follows commit), so a superseded/cancelled navigation leaves the user on the old view with an untouched URL — same as stop/ESC in a browser. Failures render `errorComponent`/`errorHandler` (the error-page equivalent), never a loading page: browsers have **no** UI-level load timeout that swaps to a skeleton — timeouts surface as error pages from network-layer failure only. Do not add TanStack-style `pendingMs`/in-app `pendingComponent` upgrades here: that is an app-convention (YouTube-style placeholder), not native semantics, and it was deliberately rejected in the 2026-08 review (also error-prone upstream — TanStack issues #1349/#1646/#2722). `pendingComponent` remains cold-start/refresh only (no old view to keep).

**Login guard:** `/editor` and `/editor/:slug` declare `beforeLoad: requireLogin` (`@native-router` ≥1.2 route guards) — it returns `'/login'` when `getCurrentUser()` is null, and the router redirects during resolve (before the navigation commits, so the URL never lands on the guarded route). `preload`/`PrefetchLink` run the same guard, so prefetching a guarded route while logged out just resolves the redirect target — no side effects.

**Auth chain:** `src/services/auth.ts` persists the user in `localStorage['painless.user']`, restores it at module load, and registers a token supplier with the HTTP layer (`http.setTokenGetter(() => currentUser?.token)`) — that is the only module-load http registration. The dependency direction is strictly auth → http; http cannot import auth (circular), hence the registration hook. The 401 handler registration moved to `bindUnauthorizedRedirect(router)` (`src/services/auth.ts`), mounted inside the Router tree by `UnauthorizedRedirect` (`src/views/index.tsx`, same pre-listen effect timing as `StackWarmer` — the cold-refresh first data request's 401 is covered too). Any 401 with a token fires it: `logout()` + `invalidate(router)` + `navigate` to `/login?redirect=<current path+search, fully encoded>` — the same chain as the Layout manual logout, with the redirect target instead of `/`; concurrent 401s navigate once (the first clears the user, later firings no-op while logged out), and a 401 while already on `/login` only logs out (a failed login attempt's 401 never fires — no token). `logout()` clears all entity caches (`clearAllCaches()`, `@/util/useQuery`) *before* `setUser(null)`: the `change` event may trigger new requests (e.g. Layout navigation), and clearing first guarantees they start from an empty, account-free cache. `src/index.tsx` side-effect imports `@/services/auth` before rendering so the very first route-`data` request after a cold refresh carries `Authorization`. Login/logout swap the module variable and emit `change` events; `Layout` subscribes via `onAuthChange` to switch the nav.

**HTTP:** All API calls go through `src/util/http.ts`, built on [`fetch-fun`](../fetch-fun) (^0.12.1, pipeable fetch toolkit). Pipeline: `baseUrl` (`VITE_API_URL` override, default `https://api.realworld.io/api/`) → JSON headers → `withTimeout(10_000)` (per-attempt budget — declared `inner of retry`, so every retry gets a fresh timeout) → `withRetry(2)` (library defaults: idempotent methods only, transient statuses 408/425/429/5xx, exponential backoff 1s→10s, respects `Retry-After`; the one deliberate exception: `createApiClient(retryMethods?)` derives a sibling `toggleClient` whitelisting POST+DELETE for effect-idempotent toggle endpoints — favorite/follow go out via `postRetryable`/`delRetryable`, entity-creating writes like addComment/saveArticle stay on the main client where POST is never replayed) → `totalTimeout(30_000)` (whole-request budget bounding all retries + backoff as one unit — without it a GET can hang for ~1min under worst-case backoff) → `withAuth` with `Token` prefix (supplier re-evaluated per attempt; empty credentials skip the `Authorization` header entirely) → `mapError`. Errors: non-2xx responses stay fetch-fun `HTTPError` with identity preserved via `withMessage` — `instanceof HTTPError`, `.status`, `.data` (field-structured `errors` object) all keep working; `.message` is rewritten for readability (API `message` first, otherwise the `errors` object joined into text). A 401 with a token present fires the registered unauthorized handler. In dev builds a `withLogging` middleware pushes Request/Response/Error events into `src/util/requestLog.ts` (DevTool request log); the `import.meta.env.DEV` branch is tree-shaken from production.

- **Async data:** Components do not call the react-toolroom hooks directly — `src/util/useQuery.ts` is the project-level data layer split into *mechanism* and *scenario assembly*. Mechanism: `createQueryCache(name, cacheTime?, opts?)` creates a per-entity cache (auto-registered in the `allCaches` registry — logout sweep and DevTool panel iterate it as the single source of truth; `opts.persist: {key, enabled}` transparently forwards to `createMemoryCacheProvider`'s persistence since react-toolroom 0.23: version-gated localStorage mirror, write-through-diff, cross-tab convergence, clear wipes storage — replaces the former template-side `attachPersistence`); `bindQueryFn(fetch, cache)` pairs one service function with one cache behind a phantom-brand `QueryFn<T, K>` type (DEV throws on rebinding a different cache). Scenario assembly: `createQueryHook({queryFn, staleTime?, initData?, mock?})` closes all options at the declaration site (`src/services/dataloaders.ts`) and returns a zero-option hook `useXxxQuery(args) → {data, loading, fetching, error, stale, refetch}`. Semantics: `loading` is *initial* loading only (per-args-key observation, `keyedLoading && keyedData === undefined` — true while THESE args are in flight with no result of their own yet, matching TanStack Query's `isLoading`; switching args to an uncached key honestly re-enters loading, and a post-comment invalidation refetch keeps `loading` false so rendered lists never flash back to a spinner), `error` is likewise keyed per args, while `fetching` is any in-flight call. The run carries a trailing `AbortSignal` (dependency changes/unmount abort the previous call, threaded through the service layer to fetch). Concurrent same-args calls are deduplicated at the *provider* level (`provider.load` atomic get-or-insert — every consumer and every channel, including route loaders via `withCache`, shares one in-flight promise per key). `hashArgs` — from react-toolroom ≥0.24 (the template's former `stableHash(stripVolatile(args))` composition, upstreamed verbatim): `stripVolatile` recursively strips `AbortSignal`s and `undefined`-valued object keys, and `stableHash` ignores `undefined`-valued keys, so the loader side (schema output with absent default keys) and the view side (component state with `undefined` props) always agree on one key. Focus/online revalidation for bfcache/snapshot-restored freshness is wired inside the scenario hook (fresh entries hit the cache without a request). Defaults: `cacheTime` 5min per entry (gcTime-aligned; `tagsCache` opts out to 1h), `staleTime` 2000ms. `refetch` deletes the cache entry first (cache bypass; rapid re-clicks each restart the request), and its identity follows `args`. Invalidation is cache-addressed: `useMutation({invalidates: [...]})` / `invalidate()` target per-entity caches (the cache object itself is the address). `opts.mock` wires the DevTool panel via `useMock` — the mock middleware must register *inside* the cache layer, which is why it is an option instead of caller-side composition; the mock config must stay constant per call site. Route-level data goes through `createDataLoader` (next section).

**Loader ↔ query shared cache (`withCache`):** route `data` loaders and `useQuery` deliberately share the **per-entity caches** (`articleCache`/`homeCache`/`commentsCache`/`tagsCache`, registry `allCaches`) — the two channels differ in *when* they trigger and whether they block (loader: navigation resolve, `pendingComponent` skeleton; query: post-mount, loading/error states), but cache and invalidation are one. `withCache(cache, keyOf, fn)` (`src/util/loaderCache.ts`) wraps a loader; the fetch × cache × keyOf × mock binding for every route is declared once in `src/services/dataloaders.ts` via `createDataLoader({fetch, cache, keyOf, mock})` → `[loader, useData, queryFn]` triple — the loader goes into the route table, the typed `useData()` hook (with `{optional: true}` overloads and a DEV "route.data === loader" identity check) replaces hand-written `useData<T>()!` casts in views, and the queryFn feeds `createQueryHook` scenario hooks. Same key-form guarantees as above (the `hashArgs` normalization), with SWR semantics: fresh hit → cached value, zero requests; stale hit → old value immediately + background revalidation via the provider's atomic `load` (in-flight shared with any channel; generation counter keeps late responses from clobbering mid-flight writes); optional `maxAge` hard expiry treats over-aged entries as a miss (no stale-first); settle flows through the cache `set` event, which `bindRefresh` (same module) fans out to `refresh(router)` microtask-debounced when a seen key's value reference actually changed — failures abort silently keeping the old value; miss → `load` promise with the route skeleton/error paths intact. That single `keyOf` declaration is what makes mutation write-through (below) address the loader's entry. Division of labor: the router viewStack decides *whether* the loader runs at all (POP within the session window replays the snapshot with zero requests); the cache decides *whether a running loader hits the network*. Two session-level freshness edges: `logout()` calls `invalidate(router)` (native-router ≥1.6) so viewStack snapshots of the old account are dropped — a later back POP re-resolves through guards + loaders instead of replaying the previous account's views; and `pageshow` with `persisted: true` (bfcache restore, no SPA event fires) triggers `refresh(router)` — loaders re-run against the cache, fresh hits cost nothing, stale ones swap in silently.

**Optimistic mutations (`cache.mutation`):** favorite (Home/Article) and follow (Article) are **cache-bound declarative pipelines** living in the service layer (`src/services/mutations.ts`), composed per cache projection since react-toolroom 0.10: `cache.mutation(spec)` with `mutate` (zero-arg service call) → `update` (synchronous optimistic step) → `apply` (field-selecting merge of the server response — only the fields the response is authoritative for, so a concurrent write to another field survives) → automatic rollback with an identity guard on failure (an entry is restored only if it still holds exactly the optimistic value). Composition: `favoriteOnHome` wraps `favoriteOnArticle` — the article layer owns the entity cache (`key: [slug]`), the home layer patches every `homeCache` page containing the slug (no `key` = patch-all-entries with miss-bail); both layers roll back independently on rejection. Views reduce to `const [favorite] = useMutation(favoriteOnHome)` plus a failure toast (`useToast`, danger variant — the rollback already restored the UI; the toast explains why). Refresh is automatic: write-throughs flow through the cache `set` event → `bindRefresh` → `refresh(router)` (see the withCache section above); views contain zero `refresh` calls. A follow success merges with the article entry via `apply` receiving the settle-time current value (peek-merge semantics built in).

**Comment refresh:** posting a comment goes through `useMutation(articleService.addComment, {invalidates: [commentsCache]})` — on success the whole `commentsCache` entity is invalidated (per-entity cache: the prefix IS the cache), and mounted `useQuery` consumers re-pull passively via the provider delete events, so `CommentList` refreshes declaratively. The form side just calls `reset(commentForm, {body: ''} )` — the comment `Textarea` is bound through `FormItem`'s control (see the Textarea note below), so the reset syncs the displayed text; `CommentList` itself has no refresh prop.

**Editor form pitfalls:** `initialValues` must be given in full for *both* create and edit modes (the create mode seeds `{title: '', description: '', body: '', tagList: []}` — `FormItem`'s control reads `getValueByPath`, and a missing `tagList` crashes `TagInput`). Since react-f0rm 0.5, `setInitialValues` compares by content — an inline object passed to `useForm({initialValues})` alone is fine (no `useMemo`, and `<Form>` ignores `initialValues` when a `form` prop is present). Fields are bound via `FormItem` (haze-ui main barrel since 1.11) render-prop: the `control` handle goes straight into the control's `value` prop (writes dispatch through `setValueByPath`, no `eventToValue` adapter needed — that was a `Field`-era workaround for `TagInput`'s non-DOM `onChange`). `useIsSubmitting` drives the `Publishing...`/`Updating...` label.

**Editor unsaved-changes guard (three channels):** `useBlocker` (react ≥1.7: returns `{state, proceed, reset}` — a vetoed navigation is parked as a pending ask on `state`) covers every leaving channel: ① in-app navigation — the predicate is `() => !isDirty(form)` (return `false` to veto); a veto parks the target in `blocker.state`, which drives the `ConfirmDialog` directly (no hand-rolled ref/state mirror); confirming resets the form to clean then `proceed()` replays the parked navigation (one-shot bypass of this blocker only), cancelling is `reset()`; ② browser back/forward (POP) — same predicate, and a vetoed POP is auto-compensated by the library with a reverse `go()`, so the URL never moves (`proceed()` there replays as a fresh push, not a history traversal); ③ full unload (refresh/close) — `beforeunload` with the legacy `returnValue` double-write (some browsers ignore `preventDefault` alone). After a successful save, `setInitialValues(form, values)` runs *before* `navigate` — otherwise live values still differ from the old initialValues and the post-save navigation itself would be vetoed.

**Textarea/Input `value` semantics depend on what you pass:** a plain string only *seeds* haze-ui's `useControl` internal state — later prop changes do NOT update the displayed text. A `Control` (e.g. `useFormControl(form, name)` or `FormItem`'s binding) makes the field fully controlled: the handle re-reads the form value every render (`useValueByPath` subscription), so external writes like `reset(form, {...})` sync the displayed text — no subtree remounting needed. Editor fields and the Article comment box use the `FormItem` bridge; see the comment-refresh mechanism above.

**Forms:** `react-f0rm` 1.1.x — `onSubmit` / `onValidSubmit` both fire only after validation passes and both are awaited (`void | Promise<void>`), so `isSubmitting` spans the entire async submission; the project uniformly uses `onSubmit`. All forms — Editor, Article comment, Login, Register — bind fields through the same `FormItem` (haze-ui main barrel since 1.11) render-prop, which renders the first field error as a `<span role='alert'>` under the field (`Field` + `FieldError` are gone). Shared validators live in `src/util/validators.ts` (`required`/`email`/`minLength` factories + `compose`); its `applyApiFieldErrors(form, e, fields)` maps the HTTP error's field-structured `data.errors` onto fields via react-f0rm's `setServerErrors` (type `'server'`, clearing prior errors first; the error is matched by duck shape — `status === 422` + `data.errors` — not `instanceof`, so the form layer stays decoupled from the HTTP library) and hides the top-level Alert when every server error landed on a field; unmappable keys stay in the Alert as fallback. The RealWorld `{message}` / `{errors: {field: string[]}}` contract is parsed by one shared module (`src/util/apiError.ts` `parseApiError` → `{message?, fieldErrors?}`) consumed by both `http.ts` (readable `.message`) and the form backfill — one contract, one parser.

**Layout:** `src/views/Layout/index.tsx` is the app shell (header, nav, `<View />` outlet) with auth-driven nav. Shared view-level patterns: `src/views/_shared/` hosts `AuthorLine`/`TagList` (avatar+username rows and tag badge lists used by Home/Article/Feed) and `useFavorite`/`useRequireAuth` (the logged-out write gate — redirect to `/login` with the current location — consumed by favorite and follow alike); the loading/error/content three-way branches of Tags/CommentList/Feed render haze-ui's `AsyncSection` (`loading` first, `Error` → `role=alert` + Retry, labels configurable); page titles use haze-ui's `useTitle` hook (sets on mount, restores the previous title on unmount).

**CSS:** Linaria (`@linaria/core`) — zero-runtime CSS-in-JS extracted at build time via `@wyw-in-js/vite`. Styles are defined with `css` tagged template literals.

**Types → JSON Schema:** `src/types/base.ts` types carry JSON Schema annotations as JSDoc tags (`@faker`, `@minimum`, `@unique`, ...). The `rollup-plugin-type-as-json-schema` plugin converts them to `.schema` files (imported from `@/types/index.schema`), which `src/util/faker.ts` uses with `json-schema-faker` + `@faker-js/faker` for dev-mode mock data. Note: `json-schema-faker` 0.6 requires the faker instance via `options.extensions` (`generate(schema, {extensions: {faker}})`) or `@faker` annotations are silently ignored.

**DevTool:** dev-only, loaded via `React.lazy(() => import('./components/DevTool'))` behind `import.meta.env.DEV` in `src/index.tsx` — the UI (and everything it pulls in) is tree-shaken out of production builds. The mock *core* lives in `src/util/mock.ts` (no static faker dependency): config state + `getMockConfig(s)`/`setMockConfig`/`onMockConfigChange` + `mockViewData` + `useMock`; production bypasses entirely (`mockViewData` returns the original fn, `useMock` registers nothing) and faker generation uses branch-local `await import('./faker')`, so the faker/json-schema-faker chain never enters the main chunk. `setMockConfig` is a pure state write (cache clearing happens at real user interaction points — DevTool mode switch, panel Refresh, cache Clear) — mocks take precedence over the loader's fresh `withCache` hits only when the cache is actually dropped. The panel (`src/components/DevTool.tsx`) lists each registered dataset with `empty` (mock only when the API errors or returns nothing) / `always` / `disabled` modes, and hosts the **cache view** (per-entity `allCaches` snapshots: entry count, hashed key, age, `⏳ in-flight` badges, recent set/delete/clear event stream, Clear button) and the **request log** (`src/util/requestLog.ts` ring buffer fed by the dev-only `withLogging` middleware in `src/util/http.ts` — Request/Response/Error events, newest-first, status-colored), and since core 1.16 the **routes/viewStack view** (observability surface `onDebug`/`getDebugInfo`: a snapshot row — current `to`, history `index`, session-window `stackDepth`/`baseIndex`, `snapshots` held, in-flight `resolving` chain or `idle` — plus a nav-event timeline of the most recent navigations, nav-start/commit/supersede/cancel/error with durations and the `replay` flag marking viewStack-served POPs; the router instance is published from inside the Router tree by the DEV-gated `RouterHost` probe into `src/util/routerHost.ts`, since the panel renders outside the Router where `useRouter()` has no context — the subscription mounts/unmounts with the panel like the other views).

**Testing:** Vitest + Testing Library. Component tests (`Home` incl. direct `Tags` tests, `Editor`, `Article`, `Layout`, `PreviewLink`, `Loading`, `RouterError`, `NotFound`, `DevTool`) mock the *service layer*, not the network, so real view logic is exercised; unit tests cover `useQuery`, `loaderCache`, `http`, `faker`, `auth`, `article`, and `mutations` (favorite two-layer rollback + follow peek-merge, driven against real per-entity caches); form tests (`Login/form.test.tsx`, `Register/form.test.tsx`) cover validator wiring and server-error field backfill. Home/Article tests model the write-through chain by mocking `refresh` as a re-render broadcast and reading `useData` straight from the per-entity caches. The vitest pipeline registers the same `rollup-plugin-type-as-json-schema` as the app build, so `@/types/*.schema` virtual modules resolve in tests; since haze-ui ≥1.11.1 the dist is pure ESM with zero CSS specifiers, so vitest consumes it directly (no `server.deps.inline`) — per-test `vi.mock('haze-ui')` stubs remain deliberate view isolation, not a compatibility workaround.

## JSX Extensions

Babel plugins `transform-jsx-condition` and `transform-jsx-class` enable extended JSX syntax:
- `x-if`, `x-elseif`, `x-else` — conditional rendering as JSX attributes
- `x-class` — conditional className merging

These are allowed by ESLint (no `react/no-unknown-property` rule).

## Component State Pattern: `useControl`

`react-use-control` (direct dependency; haze-ui re-exports `useControl` too) unifies controlled/uncontrolled state behind a **control object**. Use it for component state exposed to hosts via props. Do NOT use it to wrap state already managed by another library (e.g. react-f0rm).

State exposed via props follows the `Control<T> | T` convention (identical to every stateful haze-ui component — see haze-ui `lib/CONVENTIONS.md`):

```tsx
// Good — state a host may want to steer
type Props = {open?: Control<boolean> | boolean};

function DevToolInner({open: openControl}: {open?: Control<boolean> | boolean}) {
  const [open, setOpen] = useControl(openControl as Control<boolean>, false);
  // ...
}
```

- Destructure the prop with an alias (`open: openControl`) to avoid shadowing; the `as Control<boolean>` cast is required by react-use-control 1.3.x typings (first param is `Control<T> | Nullish`; at runtime `isControl` routes plain values to the uncontrolled-seed path)
- The third tuple element is the control to pass down/share: `const [open, setOpen, openCtrl] = useControl(false)`
- A control prop must be identity-stable across renders — dev builds throw if the same mounted hook receives a different control object
- Adopted by `DevTool` (`open` — lets E2E/hotkeys open the panel) and `PreviewLink` (`visible` — lets hosts drive preview on touch devices); form fields use the same token via `FormItem`'s `control`

Deliberately NOT converted (do not "fix" these):

- read-only receivers — `Preview` takes plain `visible: boolean`; a control earns its keep only when multiple parties read *and write*
- state owned by another library — react-f0rm owns form fields (pass `FormItem`'s `control` through instead)
- page-local state — view-level `error` messages stay `useState`

```tsx
// Bad — form state is already managed by react-f0rm
function FormField() {
  const {value, onChange} = useField({name: 'email'});
  const [controlled] = useControl(value, ''); // redundant!
  // ...
}
```

**Rule of thumb:** If a library already owns the state (react-f0rm for forms, react-toolroom for async data), pass it through directly. `useControl` is for component-internal state that benefits from the controlled/uncontrolled pattern.
